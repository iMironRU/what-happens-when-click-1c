# Инструкции для Claude Code

Технический лонгрид «Что происходит, когда я кликаю по ярлыку 1С».
Части 00–04 готовы, 05–10 в доработке (таблица статусов — в `docs/plan.md`).

Перед любым действием прочитай контекст:

- **`spec/constitution.md`** — жанр, маршрут, рамки, честная граница знания.
  Если предложение уводит с маршрута — откажись от него.
- **`spec/specification.md`** — для кого книга, что читатель знает на входе,
  метрики успеха, ограничения.
- **`spec/decisions.md`** — лог решений.
- **`docs/style-guide.md`** — канон серии плюс надстройка лонгрида: **здесь нет
  упражнений и контрольных вопросов**, вместо них — раздел «Где это видно».
- **`docs/plan.md`** — маршрут по частям и статусы.

---

## Структура репозитория

```
chapters/
  NN_slug/
    NN-01_slug.md   ← первый файл части: начинается с «# Часть N. Название»
    NN-02_slug.md   ← последующие: сразу «## N.2. Название»
    NN-MM_itog.md   ← последний файл части
```

Frontmatter обязателен:

```yaml
---
status: review     # draft | review | ready
---
```

## Главное правило жанра

**Порядок событий — единственный порядок изложения.** Книга идёт по маршруту
одного запуска: щелчок → лаунчер → выбор базы → сеть → аутентификация →
подготовка решения → компиляция → сеанс → интерфейс. Материал, не лежащий на
маршруте, — либо короткое отступление с явной пометкой, либо приложение.

Каждый шаг должен быть **диагностируем**: где это видно — лог, файл, счётчик.
Если шаг наблюдать нельзя, это говорится прямо.

Если механизм не документирован — так и пишем. Реконструкции «вероятно, внутри
устроено так» запрещены.

## Команды

### `/book-write N.N [тема]`
Порядок: конституция → спецификация → план → соседние параграфы → стиль.
`status: draft` в frontmatter.

### `/book-analyze N.N`
Конституция → спецификация → стиль → консистентность с соседями по маршруту.

### `/book-plan часть-N`
Уточнить состав части; решения — в `spec/decisions.md`.

## Что не делать

- Не добавлять упражнения и контрольные вопросы — это не учебник.
- Не уходить с маршрута ради интересной подробности.
- Не выдавать догадку о внутренностях платформы за факт.
- Не превращать сравнение с Java/C#/Node.js в оценку «лучше/хуже».
- Не менять `status: ready` без явного запроса автора.
- Не изменять `metadata.yaml` напрямую — только через `./book.sh`.
